# Spike S6: Taxpresso as a ChatGPT plugin

Question: can Taxpresso also ship for ChatGPT, as OpenAI's plugin package around the same local server, without giving up any of its rules (no network, no LLM call in our code, the dependency allowlist, AGPL)? And does the `.mcpb` work there?

Status (27 November 2026): the package builds, passes its checks and passes the offline test, started exactly as its `mcp.json` says. The same day, once the owner had installed the ChatGPT desktop app (26.1120.50957) and signed in, the package was **installed and run through the app's own engine** (the command-line tool inside the app, `codex-cli` 0.171.0-alpha.13.2): ChatGPT's model saw the tools, read a made-up household's eight documents, asked and saved the answers, and gave the tax **to the centime**. The owner then tried it in the app's window, on a free ChatGPT account: **a plain new chat has Taxpresso's tools**, and "Open the Taxpresso dashboard" gives the dashboard's link and the right tax. Whether the dashboard can also show inside the conversation was not seen. Verdict: **go for the packaging, not ready to announce, and no-go for good for a hosted server**.

After the spike, the same day: the package got its own build of the server and the UI, in which the assistant is called ChatGPT (finding 1 and decision 5 say what was done). The sections below are the spike as it was run, when the package still carried the Claude plugin's files; where the build has changed since, the text says so.

Why now: SPEC.md section 17 puts "ChatGPT feasibility" in phase 5 (April to December 2027). The owner asked for it on 27 November 2026. This spike is that feasibility check, brought forward; it changes nothing in the `.mcpb`, the Claude plugin, the website or the spec.

The authority for every statement about ChatGPT below is OpenAI's documentation, read on 27 November 2026: [plugins/build/plugins](https://developers.openai.com/plugins/build/plugins.md), [plugins/deploy/desktop-only](https://developers.openai.com/plugins/deploy/desktop-only.md), [plugins/deploy/submission](https://developers.openai.com/plugins/deploy/submission.md), [plugins/deploy/connect-chatgpt](https://developers.openai.com/plugins/deploy/connect-chatgpt.md), [plugins/build/skills](https://developers.openai.com/plugins/build/skills.md), [plugins/build/mcp-server](https://developers.openai.com/plugins/build/mcp-server.md), the help article [Connecting custom MCP servers in ChatGPT](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt), [Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels), [MCP Apps in ChatGPT](https://developers.openai.com/apps-sdk/mcp-apps-in-chatgpt) and the [MCP page of the Codex docs](https://learn.chatgpt.com/docs/extend/mcp?surface=cli). Some of these pages are long and were read in part; where a point below rests on a part that was only summarised, it says "per the docs' summary". The two JSON schemas the package names were fetched from agent-plugins.org the same day.

## What OpenAI's documentation establishes

| Question | Answer | Where |
|---|---|---|
| Does ChatGPT install a `.mcpb`? | No. No page mentions the format or a double-click install. ChatGPT's own package is a "plugin": a folder with `plugin.json`, `skills/` and `mcp.json`. | plugins/build/plugins |
| Can a plugin carry a local server? | Yes: a `stdio` entry in `mcp.json`, the server and its dependencies inside the package. The docs' own example is `node ${PLUGIN_ROOT}/server/dist/index.js`. | plugins/deploy/desktop-only |
| Where does such a plugin run? | Only in the ChatGPT desktop app, and only in threads that run locally: Work mode and Codex. It is marked "Desktop only". Not on the web, not on a phone. | plugins/deploy/desktop-only, plugins/build/plugins |
| In ordinary Chat in the desktop app? | The docs don't say it works. Users report that the app starts a local server and lists its tools, but the Chat session never gets them, on Windows, macOS and Linux; one report says the same plugin works in Work mode. Open since 12 August 2026, last comment 25 November 2026, no maintainer answer seen. | [openai/codex issue 38162](https://github.com/openai/codex/issues/38162) |
| Can it be in OpenAI's public directory? | Only for approved partners: "Local MCP submissions are limited to approved partners", through an OpenAI representative. | plugins/deploy/desktop-only |
| How does anyone else install it? | Through a marketplace file (`~/.agents/plugins/marketplace.json`, or `.agents/plugins/marketplace.json` in a repository) that points at a folder, a git repository or an npm package, then a restart of the app; or `codex plugin marketplace add <owner/repo or folder>`. No file to double-click, no link to share, no upload for personal use. A workspace admin can publish a plugin to their own workspace. | plugins/build/plugins |
| The road into ordinary ChatGPT chat? | A remote server at a public HTTPS address ("Can I connect to a local MCP server? Not directly."). Adding one's own server is for Business, Enterprise and Edu; Pro gets read and fetch only; the page says nothing for Free, Go and Plus. | help article 12584461 |
| Secure MCP Tunnel? | Keeps the server at home, but every request passes through OpenAI's hosted tunnel endpoint, it needs platform permissions, and it "does not support public plugin submission or distribution". | api/docs/guides/secure-mcp-tunnels |
| The panel in the chat? | ChatGPT renders MCP Apps views: a `ui://` resource with the type `text/html;profile=mcp-app`, named by the tool's `_meta.ui.resourceUri`, in an iframe that talks to the host over the MCP Apps bridge and can call the server's tools. Inline, fullscreen and picture-in-picture exist. No page says it for a local server. | apps-sdk/mcp-apps-in-chatgpt |

So SPEC.md section 17's reason for waiting ("ChatGPT custom apps need a public HTTPS MCP endpoint and full write tools are limited to Business/Enterprise/Edu, which conflicts with C2") is now half true: it still holds for ordinary ChatGPT chat and the web, and it no longer holds for the desktop app's local threads. The spec is not edited here; see the decisions at the end.

## Findings

1. **The wording named Claude. Fixed after the spike (27 November 2026).** During the spike the package was the same server and the same UI, so ChatGPT and its user read "Claude" in many places. Counted on main at 68f5162:
   - Server instructions (`extension/src/instructions.ts`): none. They say "you" and "the user".
   - Tool titles and descriptions: none of the 27. (Three descriptions inside `get_status`'s output schema did: "Documents Claude has not read yet." and two more.)
   - Tool results: 38 places in the built server. In the sources: 16 in `extension/src` (8 files; `status.ts` 6, `journey.ts` 4), 10 in `packages/*/src` (5 files; `rules-ge/src/engine/final-check.ts` 4), 4 in `data/ch/2026/questions.yaml`. The very first result had one: `get_status` on an empty folder ended "Or just tell Claude about yourself."
   - The dashboard and the in-chat view: 164 places in the built view; nearly all in the `i18n*.ts` files in four languages.
   - `extension/manifest.json`: 9. The build swaps the name there (`forChatgpt`), and fails if any is left.
   - `get_status` with `detail` ended its runtime line with ", Claude plugin".

   **What was done.** The build flag has a third value, `chatgpt` (`__TAXPRESSO_DISTRIBUTION__`: `mcpb`, `plugin`, `chatgpt`), and the assistant's name comes from it: `ASSISTANT` in the server (`extension/src/config.ts`) and in the UI (`ui/src/shared/distribution.ts`). Every sentence that names the assistant takes the name from there, so there is still one source of copy:
   - The server's own sentences (`extension/src`, 16 places) and the dashboard's (148 texts: 36 in each of en, fr, de, it in the `i18n*.ts` files and `Estimate.tsx`, and one in each language in the in-chat view) are written with the constant.
   - The libraries and the questionnaire data are pure and read no build flag: the six sentences in `packages/rules-ge` (the final check and the securities list, English and French) and the four in `data/ch/2026/questions.yaml` say `{assistant}`, and the server fills the name where it takes their result (`named()` in `config.ts`: the questionnaire engines in `cantons.ts`, `finalCheck` in `final-check.ts`, `etatDesTitres` in `holdings.ts` and `wealth.ts`).
   - Written by hand for ChatGPT, because they named Claude's own apps: `open_dashboard`'s result ("while the ChatGPT desktop app is running"; where the dashboard stays: "it shows in the conversation where the app allows it; if it does not show there, give the user this link to open in a browser on this computer", which is all that apps-sdk/mcp-apps-in-chatgpt establishes: no button or pane of the app is named); the dashboard's "Taxpresso is not answering. It stops when ... closes" in four languages ("the ChatGPT desktop app", "l’application de bureau ChatGPT", "die ChatGPT-Desktop-App", "l’app desktop di ChatGPT"); the description of `runtime.distribution`. The French, German and Italian names of the app are our own translations, not checked against OpenAI's localized pages.
   - `get_status` with `detail` reports `runtime.distribution: "chatgpt"` and ends its runtime line ", ChatGPT plugin". The Claude plugin's stays `"plugin"` and ", Claude plugin"; the .mcpb's has neither, as before.
   - The two bundlers fold the flag differently. esbuild (the server and the in-chat view), which doesn't minify these builds, keeps both sides of a `?:` but folds `(flag && a) || b`: every host-specific wording is written in that form, in those two files only, so the ChatGPT build holds no "Claude" and the Claude builds hold no "ChatGPT".
   - The skill's line "Where a result or the dashboard names another assistant, it means you" is removed.

   **Counts in the built ChatGPT package, before and after** ("as a word": `\bClaude\b`):

   | | "Claude" before | "Claude" after | as a word, after | "Cowork", ".mcpb" after |
   |---|---|---|---|---|
   | `server/` | 38 | 2 | 0 | 0 (were 2 and 1) |
   | `ui/views/dashboard.html` | 164 | 10 | 0 | 0 |
   | `ui/dashboard/` | 168 | 16 | 0 | 0 |

   What is left are identifiers in code, not wording: the function `imageForClaude`, the component `AskClaude` and its `askClaude`, the text key `step.fillClaude`; and in lower case the ledger's `claude` (a value's origin, written in the user's files) and the activity keys `act.claude.*`. Renaming them would touch stored data or existing tests and changes nothing anyone reads. Fourteen code comments that reach the built files now say "the assistant".

   **What proves it.** `scripts/check-chatgpt-plugin.mjs` fails on any file of `server/` and `ui/` that names "Claude", "Cowork" or ".mcpb" as a word. `extension/test/assistant.test.ts` and `ui/src/dashboard/assistant.test.ts` hold today's sentences word for word (a sample in each language) for the flags `mcpb` and `plugin`, and for `chatgpt` require the same sentences with the name swapped, in every text of the dashboard. A one-off comparison of all 3,072 dashboard texts against the sources before the change: none differs for `mcpb` or `plugin`; 144 differ for `chatgpt`, each by the name alone. The offline test checks every tool result, the tool list, the instructions and the prompt of each package: no "Claude", "Cowork" or ".mcpb" from the ChatGPT package, no "ChatGPT" from the other two, no `{assistant}` left unfilled.

   **Still open.** `extension/manifest.json`'s listing texts are still swapped by the build (`forChatgpt`), which is fine for two short descriptions. The website and the privacy page have their own ChatGPT wording since the website change (finding 8). The test build installed in the ChatGPT app on the owner's Mac is the spike's: it has the old wording until it is rebuilt and installed again.

2. **The panel in the chat is built on the standard ChatGPT implements, but four host features are untested there.** The server declares the view the way OpenAI's page shows (`_meta.ui.resourceUri`, plus the older `ui/resourceUri` key; type `text/html;profile=mcp-app`; a CSP that allows no domain), and the view uses the standard bridge (`@modelcontextprotocol/ext-apps`). What it asks of the host, and what to watch:
   - `callServerTool` to `dashboard_api`: documented for ChatGPT ("Call a tool from the UI").
   - `_meta.ui.visibility: ["app"]` on `dashboard_api`, which hides it from the model: not mentioned in the pages read, but **honoured in the test**: ChatGPT lists 26 tools and `dashboard_api` is not one of them.
   - `ui/message` (the view's "ask" buttons put a sentence in the chat as the user's): not mentioned for ChatGPT; the view already copes with a host that lacks it.
   - `requestDisplayMode` and `openLink`: the view asks once, at the start, to float beside the chat (picture-in-picture) when the host offers it, has buttons for fullscreen and back, and opens the browser dashboard through the host. ChatGPT documents the three modes; behaviour for a local plugin is unknown.
   - If the host doesn't let a view call tools (no `serverTools` in its capabilities), the view shows a card with the link to the browser dashboard instead. That fallback exists already, so the worst case in ChatGPT is the dashboard in the browser, as in Claude Code.

3. **Node: settled by the test.** `mcp.json` starts the server with `node`. OpenAI's pages don't say where that comes from; the app does: its engine searches the user's shell `PATH` and then the app's own folder, which holds a Node (v24.22.3 in app 26.1120.50957). A user's own Node wins when there is one; otherwise the app's runs the server, and Taxpresso's whole test household ran on either. Nobody has to install Node. One trap remains: if `node` is found nowhere, the tools are simply absent and nothing says why.

4. **The tax folder.** The format has no setting the user fills in at install (the `.mcpb` has `user_config.vault_path`). The folder is `TAXPRESSO_VAULT_PATH` from the app's environment, else `~/Documents/Taxpresso`. `mcp.json` may carry an `env` (the schema allows it), and the app passes it on (seen in the test); whether `${HOME}` or other variables expand there is not documented. The app also gives the server `PLUGIN_ROOT` and `PLUGIN_DATA`. The test build's `--vault` uses `env` and, so that it holds whatever a host does, starts the server through a small file that fixes the folder first.

5. **Install and distribution are harder than the `.mcpb`, not easier.** No double-click, no listing without partner status, no share link. What works today, tried on a Mac: download a zip, unzip it, and paste two lines into Terminal that call the tool inside the ChatGPT app (`/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex plugin marketplace add <folder>`, then `... plugin add taxpresso@taxpresso`). The unzipped folder has to stay where it is: the app remembers its place. Whether the app's window offers the same without Terminal is not known. This package widens who could use Taxpresso only among people comfortable with that, until OpenAI lists local plugins for everyone or accepts Taxpresso as a partner.

6. **Ordinary ChatGPT chat stays out.** It takes remote servers only. A hosted Taxpresso would receive people's tax documents and answers on a server of ours: against C2 and against what the product promises. The tunnel doesn't change that for a public product. Recommendation: rule the hosted route out for good.

7. **The rules hold.** The package adds no code to the server beyond the assistant's name behind the build flag (finding 1): no network (the offline test passes with the guard), no LLM call, the same dependency allowlist, the same licenses and notices. Under OpenAI, the reader of documents is ChatGPT, so the sentence "Claude, inside Claude Desktop, is the only model" in `CLAUDE.md` and SPEC.md C1 would need its wording widened; the rule itself (our code never calls a model) is untouched.

8. **Privacy wording.** The website and its privacy page say that what you share goes to Claude under your Claude account. For ChatGPT it goes to OpenAI under the user's ChatGPT account and settings. Nothing is published about ChatGPT today (`README.md`: "ChatGPT isn't available yet"), and nothing should be until the page says this.

9. **Files dropped into the chat.** OpenAI documents file parameters for tools and file helpers for views (`window.openai.uploadFile`, `selectFiles`, `getFileDownloadUrl`), without saying whether they work for a local server. Not explored: SPEC.md C6 keeps documents entering through the Taxpresso folder only, and that question is being looked at for Claude first.

10. **Limits.** Codex's documented defaults are 10 s to start and 60 s per tool call (per the docs' summary); the server starts in half a second, and the whole offline test, 45 tests, takes about 17 s. No limit on the number of tools, their names or the size of a result is documented for local plugins.

## What went wrong on the way

- At first nothing on the development Mac could load the package: no ChatGPT desktop app, and `codex` on the `PATH` is a link to a removed install. The owner then installed the app and signed in; the test used the command-line tool inside the app.
- The app's window could not be looked at or clicked from the session that ran the test, so the three checks that need it are left to the owner.
- A test folder inside the repository is refused by the server ("inside a code repository"), rightly; the demo folder is `~/Documents/Taxpresso-demo`.
- The check took the test folder's path for wording ("claude" in a path): it now leaves `env` out of that check.
- The portable format is not the Claude plugin's with the files renamed: `mcp.json` needs `"type"` and a `$schema`, `plugin.json` allows no field outside its short list (OpenAI's go under `extensions["com.openai"]`), and the folder variable is `${PLUGIN_ROOT}`, not `${CLAUDE_PLUGIN_ROOT}`.
- No JSON Schema validator for the 2020-12 draft is among the project's dependencies, and a spike adds none: the check carries a small one for the keywords these two schemas use.
