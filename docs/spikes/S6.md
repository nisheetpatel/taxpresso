# Spike S6: Taxpresso as a ChatGPT plugin

Question: can Taxpresso also ship for ChatGPT, as OpenAI's plugin package around the same local server, without giving up any of its rules (no network, no LLM call in our code, the dependency allowlist, AGPL)? And does the `.mcpb` work there?

Status (27 November 2026): the package builds, passes its checks and passes the offline test, started exactly as its `mcp.json` says. **Nothing has loaded it yet**: the ChatGPT desktop app is not installed on the development Mac, and the Codex command-line tool there is a broken link left by a removed install. Trying it in the app is the [HUMAN] test plan below. Provisional verdict: **go for the packaging, not ready to announce, and no-go for good for a hosted server**.

Why now: SPEC.md section 17 puts "ChatGPT feasibility" in phase 5 (April to December 2027). The owner asked for it on 27 November 2026. This spike is that feasibility check, brought forward; it changes nothing in the `.mcpb`, the Claude plugin, the website or the spec.

The authority for every statement about ChatGPT below is OpenAI's documentation, read on 27 November 2026: [plugins/build/plugins](https://developers.openai.com/plugins/build/plugins.md), [plugins/deploy/desktop-only](https://developers.openai.com/plugins/deploy/desktop-only.md), [plugins/deploy/submission](https://developers.openai.com/plugins/deploy/submission.md), [plugins/deploy/connect-chatgpt](https://developers.openai.com/plugins/deploy/connect-chatgpt.md), [plugins/build/skills](https://developers.openai.com/plugins/build/skills.md), [plugins/build/mcp-server](https://developers.openai.com/plugins/build/mcp-server.md), the help article [Connecting custom MCP servers in ChatGPT](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt), [Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels), [MCP Apps in ChatGPT](https://developers.openai.com/apps-sdk/mcp-apps-in-chatgpt) and the [MCP page of the Codex docs](https://learn.chatgpt.com/docs/extend/mcp?surface=cli). Some of these pages are long and were read in part; where a point below rests on a part that was only summarised, it says "per the docs' summary". The two JSON schemas the package names were fetched from agent-plugins.org the same day.

## What OpenAI's documentation establishes

| Question | Answer | Where |
|---|---|---|

| Can a plugin carry a local server? | Yes: a `stdio` entry in `mcp.json`, the server and its dependencies inside the package. The docs' own example is `node ${PLUGIN_ROOT}/server/dist/index.js`. | plugins/deploy/desktop-only |
| Where does such a plugin run? | Only in the ChatGPT desktop app, and only in threads that run locally: Work mode and Codex. It is marked "Desktop only". Not on the web, not on a phone. | plugins/deploy/desktop-only, plugins/build/plugins |
| In ordinary Chat in the desktop app? | The docs don't say it works. Users report that the app starts a local server and lists its tools, but the Chat session never gets them, on Windows, macOS and Linux; one report says the same plugin works in Work mode. Open since 12 August 2026, last comment 25 November 2026, no maintainer answer seen. | [openai/codex issue 38162](https://github.com/openai/codex/issues/38162) |
| Can it be in OpenAI's public directory? | Only for approved partners: "Local MCP submissions are limited to approved partners", through an OpenAI representative. | plugins/deploy/desktop-only |
| How does anyone else install it? | Through a marketplace file (`~/.agents/plugins/marketplace.json`, or `.agents/plugins/marketplace.json` in a repository) that points at a folder, a git repository or an npm package, then a restart of the app; or `codex plugin marketplace add <owner/repo or folder>`. No file to double-click, no link to share, no upload for personal use. A workspace admin can publish a plugin to their own workspace. | plugins/build/plugins |
| The road into ordinary ChatGPT chat? | A remote server at a public HTTPS address ("Can I connect to a local MCP server? Not directly."). Adding one's own server is for Business, Enterprise and Edu; Pro gets read and fetch only; the page says nothing for Free, Go and Plus. | help article 12584461 |
| Secure MCP Tunnel? | Keeps the server at home, but every request passes through OpenAI's hosted tunnel endpoint, it needs platform permissions, and it "does not support public plugin submission or distribution". | api/docs/guides/secure-mcp-tunnels |
| The panel in the chat? | ChatGPT renders MCP Apps views: a `ui://` resource with the type `text/html;profile=mcp-app`, named by the tool's `_meta.ui.resourceUri`, in an iframe that talks to the host over the MCP Apps bridge and can call the server's tools. Inline, fullscreen and picture-in-picture exist. No page says it for a local server. | apps-sdk/mcp-apps-in-chatgpt |

So SPEC.md section 17's reason for waiting ("ChatGPT custom apps need a public HTTPS MCP endpoint and full write tools are limited to Business/Enterprise/Edu, which conflicts with C2") is now half true: it still holds for ordinary ChatGPT chat and the web, and it no longer holds for the desktop app's local threads. The spec is not edited here; see the decisions at the end.

The server and the UI are the Claude plugin's files, copied byte for byte: no new bundle, no new dependency, nothing new to allow in `extension/allowed-dependencies.json`. `pnpm build` and `pnpm build:plugin` give the same bytes as before this spike (SHA-256 over every file of `extension/dist` and `build/plugin/taxpresso`, and the plugin's zip, before and after).

## Findings

1. **The wording names Claude.** The package is the same server and the same UI, so ChatGPT and its user would read "Claude" in many places. Counted on main at 68f5162:
   - Server instructions (`extension/src/instructions.ts`): none. They say "you" and "the user".
   - Tool titles and descriptions: none of the 27.
   - Tool results: 38 places in the built server. In the sources: 16 in `extension/src` (8 files; `status.ts` 6, `journey.ts` 4), 10 in `packages/*/src` (5 files; `rules-ge/src/engine/final-check.ts` 4), 4 in `data/ch/2026/questions.yaml` (the count by source skips lines that look like comments, so it runs a little low). The very first result has one: `get_status` on an empty folder ends "Or just tell Claude about yourself."
   - The dashboard and the in-chat view: 164 places in the built view; 165 in `ui/src` outside tests, in 14 files, nearly all in the `i18n*.ts` files in four languages (`i18n.ts` 52, `i18n-pages.ts` 48, `i18n-journey.ts` 20), so about 40 sentences.
   - `extension/manifest.json`: 9. The build swaps the name there (`forChatgpt`), and fails if any is left.
   - `get_status` with `detail` ends its runtime line with ", Claude plugin": the build flag is `plugin`, since the server files are the Claude plugin's.

   For the spike, the skill tells ChatGPT that another assistant's name in a result means itself. That is a patch for a test, not something to ship. **Proposal**: a third value of the build flag (`__TAXPRESSO_DISTRIBUTION__`: `mcpb`, `plugin`, `chatgpt`) and the assistant's name behind it: one constant in the server (`extension/src/config.ts`) and one in the UI (`ui/src/shared/distribution.ts`), and `{assistant}` in the sentences that name it. Mostly mechanical; the sentences about Claude's own apps need rewording by hand ("Claude Desktop" comes 14 times in the dashboard's copy and 7 times in the server's, "Claude Code" 4 times in all), and the website and the privacy page need their own ChatGPT wording.

2. **The panel in the chat is built on the standard ChatGPT implements, but four host features are untested there.** The server declares the view the way OpenAI's page shows (`_meta.ui.resourceUri`, plus the older `ui/resourceUri` key; type `text/html;profile=mcp-app`; a CSP that allows no domain), and the view uses the standard bridge (`@modelcontextprotocol/ext-apps`). What it asks of the host, and what to watch:
   - `callServerTool` to `dashboard_api`: documented for ChatGPT ("Call a tool from the UI").
   - `_meta.ui.visibility: ["app"]` on `dashboard_api`, which hides it from the model: not mentioned in the pages read. If ChatGPT shows the tool to the model, nothing breaks: the server refuses every call without the view's key (C7), but the tool list gets one confusing entry.
   - `ui/message` (the view's "ask" buttons put a sentence in the chat as the user's): not mentioned for ChatGPT; the view already copes with a host that lacks it.
   - `requestDisplayMode` and `openLink`: the view asks once, at the start, to float beside the chat (picture-in-picture) when the host offers it, has buttons for fullscreen and back, and opens the browser dashboard through the host. ChatGPT documents the three modes; behaviour for a local plugin is unknown.
   - If the host doesn't let a view call tools (no `serverTools` in its capabilities), the view shows a card with the link to the browser dashboard instead. That fallback exists already, so the worst case in ChatGPT is the dashboard in the browser, as in Claude Code.

3. **Node.** `mcp.json` starts the server with `node`. OpenAI's pages don't say whether the desktop app brings a Node of its own or uses the computer's, nor which `PATH` it searches. On a Mac, an app started from the Dock doesn't see a shell's `PATH`, so a Node installed with nvm may not be found. Claude Desktop runs a `.mcpb` on its own Node; here that is an open question, and for an ordinary user "install Node first" would be one more step.

4. **The tax folder.** The format has no setting the user fills in at install (the `.mcpb` has `user_config.vault_path`). The folder is `TAXPRESSO_VAULT_PATH` from the app's environment, else `~/Documents/Taxpresso`. `mcp.json` may carry an `env` (the schema allows it), which the test build's `--vault` uses; whether `${HOME}` or other variables expand there is not documented.

5. **Install and distribution are harder than the `.mcpb`, not easier.** No double-click, no listing without partner status, no share link. A person outside the project would edit a JSON file in their home folder or run a `codex` command. This package widens who could use Taxpresso only among people comfortable with that, until OpenAI lists local plugins for everyone or accepts Taxpresso as a partner.

6. **Ordinary ChatGPT chat stays out.** It takes remote servers only. A hosted Taxpresso would receive people's tax documents and answers on a server of ours: against C2 and against what the product promises. The tunnel doesn't change that for a public product. Recommendation: rule the hosted route out for good.

7. **The rules hold.** The package adds no code to the server: no network (the offline test passes with the guard), no LLM call, the same dependency allowlist, the same licenses and notices. Under OpenAI, the reader of documents is ChatGPT, so the sentence "Claude, inside Claude Desktop, is the only model" in `CLAUDE.md` and SPEC.md C1 would need its wording widened; the rule itself (our code never calls a model) is untouched.

8. **Privacy wording.** The website and its privacy page say that what you share goes to Claude under your Claude account. For ChatGPT it goes to OpenAI under the user's ChatGPT account and settings. Nothing is published about ChatGPT today (`README.md`: "ChatGPT isn't available yet"), and nothing should be until the page says this.

9. **Files dropped into the chat.** OpenAI documents file parameters for tools and file helpers for views (`window.openai.uploadFile`, `selectFiles`, `getFileDownloadUrl`), without saying whether they work for a local server. Not explored: SPEC.md C6 keeps documents entering through the Taxpresso folder only, and that question is being looked at for Claude first.

10. **Limits.** Codex's documented defaults are 10 s to start and 60 s per tool call (per the docs' summary); the server starts in half a second, and the whole offline test, 45 tests, takes about 17 s. No limit on the number of tools, their names or the size of a result is documented for local plugins.

## What went wrong on the way

- Nothing on the development Mac can load the package: no ChatGPT desktop app, and `codex` on the `PATH` is a link to a removed install. Neither was installed for the spike, and no OpenAI account was used.
- The portable format is not the Claude plugin's with the files renamed: `mcp.json` needs `"type"` and a `$schema`, `plugin.json` allows no field outside its short list (OpenAI's go under `extensions["com.openai"]`), and the folder variable is `${PLUGIN_ROOT}`, not `${CLAUDE_PLUGIN_ROOT}`.
- No JSON Schema validator for the 2020-12 draft is among the project's dependencies, and a spike adds none: the check carries a small one for the keywords these two schemas use.

## Open questions and decisions for the owner

1. **Go on with ChatGPT now, or leave it for phase 5?** The packaging is done and cheap to keep. What it needs before anyone outside can use it: the [HUMAN] test, the wording (finding 1), an answer on Node (finding 3) and a way to install that isn't a JSON file (finding 5).
2. **SPEC.md section 17, phase 5** gives a reason that is half out of date. Proposed wording: "ChatGPT: a plugin with the local server runs in the ChatGPT desktop app's local threads only (spike S6); ordinary ChatGPT chat needs a hosted server, which C2 rules out."
3. **Ask OpenAI for partner status?** It is the only way into their directory with a local server.
4. **The hosted route**: rule it out in the spec, so the question doesn't come back.
5. **If the package stays**: add the three commands to `CLAUDE.md` and to CI, give the server and the UI their own build flag value, and widen "Claude is the only model" in `CLAUDE.md` and C1 to "the user's own assistant".

## Go / no-go

- **Go** for the packaging: the same server and UI, every hard rule kept, checks and the offline test green.
- **Not ready** to announce or distribute: untested in the app; the wording names Claude; the install is a developer's.
- **No-go** for ordinary ChatGPT chat and for any hosted server.
