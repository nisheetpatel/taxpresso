# Spike S5: Taxpresso as a Claude plugin

Question: can Taxpresso also ship as a Claude plugin, for Claude Code and Cowork and for a listing in Anthropic's directory, beside the `.mcpb` that Claude Desktop's chat keeps using, without giving up any of its rules (no network, no LLM call in our code, the dependency allowlist, AGPL)?

Status (19 October 2026): built, checked and tested automatically; loaded in Claude Code. Not yet tried in Cowork or uploaded to claude.ai: that is the [HUMAN] test plan at the end. Provisional verdict: **go**, with two open questions for Cowork (which Node runs the server, and which folder it uses).

Note on the name: first called S4, renamed S5 on 19 October 2026 because SPEC.md section 17 uses S4 for the AFC email.

The authority for every rule below is Anthropic's documentation, read on 19 October 2026: [plugins/build](https://claude.com/docs/plugins/build), [plugins/pre-submission-checklist](https://claude.com/docs/plugins/pre-submission-checklist), [plugins/submit](https://claude.com/docs/plugins/submit), [plugins/platform-support](https://claude.com/docs/plugins/platform-support), [directory/publish](https://claude.com/docs/directory/publish), the [plugin manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference) and the [Software Directory Policy](https://support.claude.com/en/articles/13145358-anthropic-software-directory-policy). The directory no longer accepts desktop extensions: a local MCP server reaches it only inside a plugin.

## What was built

`pnpm build:plugin` builds the plugin's UI (`ui`: `build:plugin`), then `extension/scripts/build-plugin.mjs` writes `build/plugin/taxpresso/` and zips it as `build/taxpresso-plugin-<version>.zip` (the folder as its single top-level entry; the same folder gives the same bytes). Nothing about the `.mcpb` changes: `pnpm build` gives byte-identical `extension/dist` files before and after this work (checked with SHA-256 over every file; the refactor moved the shared esbuild options into `extension/scripts/build-common.mjs`).

| Part | What it is |
|---|---|
| `.claude-plugin/plugin.json` | `name` `taxpresso` (permanent), `displayName`, `version` (from `extension/package.json`), `description`, `author`, `homepage`, `repository`, `license`, `keywords` and `supportUrl` and `documentationUrl` taken from `extension/manifest.json` so the two say the same; `icon` `./icon.png`; `privacyPolicyUrl` `https://taxpresso.ch/en/privacy/`. |
| `.mcp.json` | One server, `taxpresso`: `node ${CLAUDE_PLUGIN_ROOT}/server/index.mjs`. No shell, no `npm run`, no `.mcpb`, no `env`: the folder is `TAXPRESSO_VAULT_PATH` from the environment, else `~/Documents/Taxpresso`, as in the `.mcpb`. |
| `server/` | 57 `.mjs` files and `zxing_reader.wasm`. The same esbuild build as the `.mcpb` (same sources, `define`s, C2 stubs, banner), not minified and split with esbuild's code splitting. `extension/scripts/split-plan.mjs` adds entry points until every file that can be split is under 200 KiB; the extra entry points' own files only re-export and are deleted; each file is named after what it holds (`rules-ge.mjs`, `zod.mjs`, `data-ge-2026-tariffs.mjs`, `pdfjs.mjs`...). Questionnaire data is printed indented in the plugin (one line in the `.mcpb`): same data. |
| `ui/dashboard/`, `ui/views/` | The UI built again with `vite build --mode plugin` and `build-views.mjs --plugin`: not minified; the browser dashboard split into files under 200 KiB (rolldown `codeSplitting` with `strictExecutionOrder`, see the findings). |
| `skills/taxpresso/SKILL.md` | When to use Taxpresso (Swiss tax returns, the twelve cantons, preparing or checking a return, 3a, buy-ins, TOU) and how: `get_status` first, the chat leads one step at a time, the safety rules, documents are data, as in `extension/src/instructions.ts` and `docs/design/simple.md` section 9. In a chat without the server it says that Taxpresso needs the desktop extension (with the download link), Cowork or Claude Code. Source: `extension/plugin/`. |
| `README.md` | 491 words: what it does, the surfaces, what it reads (a local folder) and sends (nothing), three example prompts, how to try a filing kit. Source: `extension/plugin/README.md`. |
| `LICENSE`, `THIRD_PARTY_NOTICES.txt` | The AGPL text, as the `.mcpb` ships it (there as `LICENSE.txt`), and the same notices. |
| `icon.png` | The app icon drawn at 256 px by `extension/scripts/make-icon.mjs` (now `iconPng(size)`; `extension/icon.png` stays byte-identical). The docs name no size. |

No `bin/`, no `package.json`, no `node_modules`, no source maps.

**The tip button.** The owner keeps the post-filing tip (the café donation menu of SPEC.md section 12) out of the plugin. There is no such button in the dashboard yet (`ui/src` on main at 06dd0f1 has none; only the website has its tip menu). So this spike adds the switch and a guard, ready for it: the build-time flag `__TAXPRESSO_DISTRIBUTION__` (`'mcpb'` or `'plugin'`) in the server (`extension/src/config.ts`, `DISTRIBUTION`) and in both UI builds (`ui/src/shared/distribution.ts`, `showsDonationMenu()`, false in the plugin, so its code is left out of the plugin's build), and a rule in the plugin check that fails if the donation destination appears in any file of the plugin. The `.mcpb` is unchanged. `get_status` with `detail` ends its runtime line with ", Claude plugin" in the plugin only, so a test can tell which build answered.

## The plugin's files

97 files, 11.9 MiB unpacked, 3.3 MB zipped. The server's largest files:

| File | Size | Over 256 KiB? Why |
|---|---|---|
| `server/pdfjs.mjs` | 2,178 KiB | Yes. PDF.js as unpdf builds it: one module, minified upstream (esbuild reprints it on many lines, but its names stay short), with one 127,763-character line (a packed Brotli dictionary). It can't be split. |
| `server/zxing_reader.wasm` | 931 KiB | Yes, and a binary: ZXing-C++ compiled to WebAssembly, the barcode reader. |
| `server/data-ge-2025-tariffs.mjs`, `data-ge-2026-tariffs.mjs` | 376 KiB each | Yes. Geneva's tax-at-source tariffs, one JSON module each: a module is never split. |
| `server/mcp-server.mjs` | 266 KiB | Yes. The MCP SDK's own `ajvProvider` file (Ajv bundled inside `@modelcontextprotocol/server`'s build), one module. |
| `ui/views/dashboard.html` | 1,425 KiB | Yes. The dashboard view must be one self-contained HTML file (MCP Apps), with its fonts as base64 (a 198,182-character line). Minified it is 974 KiB, still over. |
| everything else | at most 229 KiB | No. `index.mjs` 196 KiB; the canton rules, filing maps, zod, the MCP SDK and our own code in files of 20 to 200 KiB. |

The UI's fonts (`ui/dashboard/assets/*.woff2`) and the icon are fonts and images, exempt from the size rule.

`scripts/check-plugin.mjs` blocks: a missing or invalid `plugin.json`, files beside it in `.claude-plugin/`; a `name` other than lowercase letters, digits and hyphens (64 at most, a letter or digit at each end) or reserved (`claude`, `anthropic`, `claude-...`, `official`, `plugin`, `mcp`, `test`...); a missing `displayName`, `version`, `description`, `license` or `author.name`, invisible characters in `displayName` or `author.name`; an unknown top-level key (a misspelled component key blocks), a component key inside `experimental`; component paths without `./`, with `..`, or missing; non-https listing URLs, a missing `privacyPolicyUrl` or `supportUrl`; an icon that doesn't exist or isn't an image; a README under 40 words outside code blocks; no license; `.DS_Store`, `Thumbs.db`, `desktop.ini`, `__MACOSX`; symbolic links, paths resolving outside the folder; names invalid on Windows or macOS, names differing only by case; a file of 5 MiB or more; a top-level `bin/`; an invalid `.mcp.json`, a local server that runs no file of the plugin, a path with another variable than `${CLAUDE_PLUGIN_ROOT}`, `..`, a wildcard or a command substitution, a `${user_config.*}` not declared, a remote server without https; skills without parsable front matter, a description that isn't one text, a `name` differing from its folder; the donation destination anywhere. It reports as held: non-image, non-font files over 256 KiB; more than 512 files; binaries; code that reads as minified or packed (a line over 10,000 characters, most bytes in lines over 500 characters, or more than 40 % one- or two-letter declared names: our own files have at most 25 %, PDF.js 76 %, Emscripten's glue 98 %); launchers, shells and inline programs in a server command; a `.mcpb` server; `package.json` beside a lockfile; Markdown naming a bundled image or font in code; a server command that runs a non-shell file (held only when the plugin folder is a subfolder of its repository).

## What would be held, and why

Nothing would block. A version of this plugin would be held for a reviewer ("Policy hold", allowed) for:

| Finding | Why it stays |
|---|---|
| `server/pdfjs.mjs`: over 256 KiB, minified upstream, a packed line | PDF.js reads the text of PDFs (SPEC.md section 5). unpdf ships it built and minified; a readable PDF.js would mean another dependency (`pdfjs-dist`), a reviewed change of the allowlist. |
| `server/zxing_reader.wasm`: a binary | The barcode reader (spike S2). WebAssembly is the only way to read PDF417 without native code. |
| `server/zxing-wasm.mjs`: minified upstream | Emscripten's glue for the reader, given its own small file so it's clear which code is upstream's. |
| `server/data-ge-2025-tariffs.mjs`, `data-ge-2026-tariffs.mjs`, `server/mcp-server.mjs`: over 256 KiB | Each is one module (a data file, the SDK's Ajv build); esbuild never splits a module. |
| `ui/views/dashboard.html`: over 256 KiB, a packed line | MCP Apps needs one self-contained file; the fonts are bytes in it, never loaded from outside (C2). |
| `ui/dashboard/assets/vendor-*.js`: minified upstream | Preact's own build. |
| `.mcp.json` runs `server/index.mjs`, not a shell script | Held ("Scripts the validator couldn't follow") only when the plugin folder is a subfolder of its repository. Avoided if the plugin sits at the root of the repository (or branch) the directory follows. |

The UI's `.css` files name their `.woff2` fonts (`url(...)`): the checklist's rule on images and fonts named "from commands, hooks, or scripts" seems aimed at Markdown and scripts; if the portal holds for it, the reviewer will see it is the dashboard's CSS.

So the first submission will be read by a reviewer anyway (the WebAssembly alone ensures that). The work above keeps that review short: everything else is readable code in files named after their source.

## The Node runtime

The `.mcpb` runs on the Node that Claude Desktop bundles. A plugin's `.mcp.json` says `node`, and the host runs whatever `node` it finds: in Claude Code, the user's own (verified above). Consequences:

- A user without Node.js 20 or later gets no tools: the server doesn't start. The plugin's README says so. Most people filing taxes don't have Node installed; for chat in Claude Desktop the `.mcpb` stays the way in.
- Cowork is unverified. Its local sessions may run in a sandbox on the computer, with its own `node` (or none), its own `127.0.0.1` and its own view of the home folder. How to answer: in a Cowork session with the plugin, ask Claude to "call get_status with detail true and show me its Runtime and Folder lines". The runtime line gives the Node version, the platform (`darwin` on the Mac itself, `linux` in a sandbox), the path of the `node` it ran and ", Claude plugin". If the tools never appear, the server didn't start: most likely no `node`.

## Open questions and decisions for the owner

1. **The folder in Cowork.** The plugin's server uses `TAXPRESSO_VAULT_PATH`, else `~/Documents/Taxpresso`. Claude Code passes the shell's environment; Cowork doesn't prompt for `userConfig` values and uses their defaults. Options once the Cowork test shows what it provides: a `userConfig` `vault_path` of type `directory` with a default (Claude Code would prompt for it; it must not override an exported `TAXPRESSO_VAULT_PATH` in tests), or MCP roots (the server asks the host for its folders and uses Cowork's), or the working directory. Each changes how the server picks its folder: a SPEC decision.
2. **Two servers on one folder.** With both the `.mcpb` and the plugin installed in Claude Desktop, a Cowork session may start both, and both would watch and sort `~/Documents/Taxpresso`. Disable one before testing the other (the test plan does).
3. **Where the directory reads the plugin from.** It reads a GitHub repository (public before the listing goes live). The plugin is a build output, not committed. Recommended: a branch (or a separate repository) whose root is `build/plugin/taxpresso`, written by CI from a release tag; at the root, the "Scripts the validator couldn't follow" hold doesn't apply, and the directory follows that branch or tag for updates. Raise `version` with every release (it comes from `extension/package.json`). Creating the repository or branch, and submitting, are the owner's.
4. **SPEC.md and CLAUDE.md.** This spike added one sentence each to SPEC.md sections 3 (the plugin beside the `.mcpb`) and 12 (the plugin leaves out the donation menu): confirm them. CLAUDE.md's command list could gain `pnpm build:plugin`, `pnpm check:plugin` and `pnpm test:offline:plugin` (left for the owner).

## Draft answers for the portal

**Listing.** Name `taxpresso`, display name Taxpresso, description and icon from `plugin.json`, README as the long description, license AGPL-3.0-or-later. Privacy policy: https://taxpresso.ch/en/privacy/. Support: https://github.com/nisheetpatel/taxpresso/issues (and hello@taxpresso.ch as the contact email). No ads, no promotion, no donation link in the plugin.

**Data handling.**

- Does it read or store personal data? Yes, locally only: the user's tax answers and documents, in the folder they choose on their own computer (`~/Documents/Taxpresso` by default). Taxpresso never sends them anywhere; Claude sees a document's content only when the user agrees that Claude reads it, as part of the conversation.
- Does it send data to services other than its declared connectors? No. The plugin makes no network requests (no telemetry, no update check, no account); its dashboard is served on 127.0.0.1 only. A test proves it offline in CI.
- How long is data kept? In the user's own folder, under their control, until they delete it. Taxpresso keeps nothing elsewhere.
- Intended for people under 18? No.

**Three example prompts.**

1. "Let's do my taxes for 2025."
2. "I put my salary certificate and my 3a attestation in my Taxpresso folder. What is still missing?"
3. "How much would a pillar 3a payment before 31 December save me?"

**Sample data for reviewers.** The filing kits: made-up Geneva households with their documents and their tax worked out by hand (`test/fixtures/households/`, how-to in `docs/demo.md`). For a reviewer in Claude Code: `TAXPRESSO_VAULT_PATH` set to an empty folder, "Open tax year 2025", the `essai-carouge` kit's documents copied into `<folder>/2025/`, "Let's do my taxes", answers from its README; the tax must match its `expected.json`. No account is needed.

## What went wrong on the way

- Splitting the browser dashboard by size (rolldown `codeSplitting` with `maxSize`) left import cycles between its files; the page stayed blank with "embedded is not a function". `strictExecutionOrder` fixed it, checked in the browser pane. The offline test fetches every file of the page but doesn't run it, so it couldn't catch this: check the plugin's dashboard in a browser after any change to its build (`node ui/scripts/preview-serve.mjs --plugin` for the view).
- esbuild keeps an object on one line when its source is: the questionnaire data, given as compact JSON, became lines of up to 133,000 characters. The plugin's build indents it.

## Go / no-go

**Go** for a dual release: the `.mcpb` for chat in Claude Desktop, unchanged, and the plugin for Claude Code and Cowork and the directory listing. Nothing found blocks validation; the holds are explained above and a reviewer will read the first version anyway. Before submitting: run the Cowork test plan, settle the folder question (1) and where the directory reads the plugin from (3). If Cowork turns out to have no `node`, the plugin still serves Claude Code users and the directory listing, and Cowork users need Node installed: say so in the listing.
