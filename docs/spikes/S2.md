# Spike S2: barcodes (salary certificate and bank e-tax statement)

Question: can Taxpresso read the 2D barcode of a salary certificate and of a bank e-tax statement on the user's computer, with WebAssembly decoders and no network, and turn them into verified values? What does the salary certificate barcode carry?

Status (14 October 2026): built and tested on synthetic documents. Real salary certificates were checked outside the repository by the human (format facts only); no real bank e-tax statement with a barcode was available. Verdict: **go** for salary certificates, **go** for e-tax statements built from the standard, with the compression question still open until a real statement is read.

## Sources found

The salary certificate barcode has an official specification after all. It is not on the ESTV or CSI pages (docs/sources/standards/NOTES.md), but in the Swissdec salary standard (ELM), made jointly with the Conférence suisse des impôts and the AFC:

| Manifest id | What it settles |
|---|---|
| `std-swissdec-elm5-lohnausweis-richtlinien-fr` | ZIP archive, ELM 5.0. `TaxAccountingOverview_f.pdf` p. 35: the XML goes into an Info-ZIP archive (java.util.zip) with one entry named `txab`. p. 36-37: the 14 control bytes. `schema/SalaryDeclarationTxAB.xsd` and the two files it includes: the XML, each element documenting its box on form 11. |
| `std-swissdec-elm6-barcode-annexe5` | ZIP archive, ELM 6.0 (6 March 2026). `Richtlinien_Barcode_fr.pdf` p. 10-11: the same ZIP and control bytes. A new namespace (`urn:ch:swissdec:elm:v6:20260306:SalaryDeclarationTxAB`); S and A gain `CreationDate` and `@addresseeIDRef`. |
| `std-eCH-0196-v2-2-0-xsd` | The e-tax statement schema `eCH-0196-2-2.xsd` (namespace `http://www.ech.ch/xmlns/eCH-0196/2`). |
| `std-eCH-0196-v2-2-0-fr`, `std-eCH-0196-v2-2-0-wegleitung-de` | The e-tax statement main document and technical guide (p. 36: segment images at 1 x 1 pixel per element; p. 37: read from the last page back). |

Already in the library and used: `std-eCH-0270-codes-barres-generation` (p. 9: PDF417 Structured Append, 290 x 35 pixel segments; p. 11: last page first), `std-eCH-0196-barcode-annex-v2-2-0` (p. 6-7: ZLIB, 13 columns, 35 rows, EC level 4, PDFMacroFileName and PDFMacroFileId), `std-lohnausweis-wegleitung-2026-fr` (boxes and Cm), `ge-2025-guide-declaration-pp` (p. 37-43: accounts, debts, securities, "relevés fiscaux").

All were fetched with `node scripts/fetch-sources.mjs --canton std` (the standards folder's code is `STD`, not `standards`).

## The salary certificate barcode (Swissdec TxAB)

Each PDF417 symbol (one usually; more when the data doesn't fit, cut anywhere and joined in order) starts with 14 control bytes:

| Bytes | Meaning (TaxAccountingOverview_f.pdf p. 36-37) |
|---|---|
| 1-4 | Identification, the same for every symbol of one certificate (random) |
| 5 | Compression: `z` (0x7a) = Info-ZIP, the only one defined |
| 6-8 | Size of this symbol's data, the 14 bytes included, big-endian |
| 9 | Page control: 1 for the first, 2 for the following ones |
| 10 | Version of the control bytes: 3 |
| 11-12 | This symbol's number, one decimal digit per byte |
| 13-14 | Number of symbols, one decimal digit per byte |

The bytes observed on the real certificates match this layout exactly: the four bytes that differ per certificate are the identification, and the byte that varied is the low byte of the size. The ZIP is written by java.util.zip with sizes in a data descriptor (flag bit 3), so the reader takes them from the central directory.

Taxpresso reads the control bytes when they follow this layout (and joins several symbols by their numbers, ignoring symbols that carry only the control bytes, which the guide says are printed on extra pages); otherwise it looks for the ZIP signature and keeps the bytes before it for diagnostics only.

Each element maps to a key whose box comes from the salary certificate guide (a test checks the schema's box and the key's box agree):

| TxAB element (S) | Box | Key |
|---|---|---|
| Period/from, Period/until | E | document period, tax year |
| FreeTransport, CanteenLunchCheck | F, G | `salary.free_transport`, `salary.canteen` (false when absent) |
| Income | 1 | `salary.base` |
| FringeBenefits/FoodLodging, CompanyCar, Other/Sum | 2.1, 2.2, 2.3 | `salary.board_lodging`, `salary.company_car`, `salary.other_fringe` |
| SporadicBenefits/Sum, CapitalPayment/Sum | 3, 4 | `salary.non_periodic`, `salary.capital` |
| OwnershipRight, BoardOfDirectorsRemuneration, OtherBenefits/Sum | 5, 6, 7 | `salary.participations`, `salary.board_fees`, `salary.other_benefits` |
| GrossIncome | 8 | `salary.gross` |
| AHV-ALV-NBUV-AVS-AC-AANP-Contribution | 9 | `salary.social_contributions` |
| BVG-LPP-Contribution/Regular, Purchase | 10.1, 10.2 | `salary.lpp_ordinary`, `salary.lpp_buyin` |
| NetIncome, DeductionAtSource | 11, 12 | `salary.net`, `salary.source_tax` |
| Charges/Effective/TravelFoodAccommodation, Other/Sum | 13.1.1, 13.1.2 | `salary.expenses_travel`, `salary.expenses_other` |
| Charges/LumpSum/Representation, Car, Other/Sum | 13.2.1, 13.2.2, 13.2.3 | `salary.allowance_*` |

A pension certificate (`A`, attestation de rentes) gives `pension.amount` (box 8) and `pension.type` occupational (the guide p. 6, Cm 1: rentes du deuxième pilier). Employee participation forms (`OA`, `OB`, `OC`) are left to Claude.

Schema checks done by hand (no validator ships): element order and required elements of every sequence, amounts exactly `-?digits.dd` (SalaryAmountType), dates, SID and SysV lengths, name and ZIP lengths, the AHV number format, the canton list, the ELM 6.0 creation date and addressee. Anything that fails: not verified, and the document goes to the text layer and Claude. Relaxed on purpose: a missing `Company` element (the schema requires it; it carries no box) is accepted and noted in the diagnostics. Decision for the lead below.

## The e-tax statement barcode (eCH-0196), from the standard alone

- Segments: ZXing reports each Macro PDF417 symbol's segment index, segment count (from the optional field, else 0) and file id; the last segment's count is its index + 1 (it carries the terminator). Taxpresso groups by file id, orders by index, requires every index, accepts duplicates only if identical, and joins. A plain (non-macro) symbol is a one-segment statement.
- Compression: ZLIB, ZIP, GZIP, raw deflate or none, detected from the first bytes and reported (`diagnostics.ech0196.compression`), with a 32 MB cap on the output. Still open: which one real statements use (the annex says ZLIB, eCH-0270 "ZIP"). A third-party open-source generator, OpenSteuerAuszug, writes ZLIB; that is not an official source.
- Schema checks by hand: element order, required attributes and their types (decimal, date, dateTime, year, ISO currency and country codes, quotation type, security category), ISIN length and check digit, xs:ID shape of the statement id; elements and attributes in other namespaces are allowed, as the schema's `xs:any ##other` allows bank extensions. Not checked: the types imported from eCH-0007, eCH-0008, eCH-0010 and eCH-0097 beyond a basic shape, `xs:unique` constraints, and whether totals add up.
- Values (all verified, household): the statement's totals per "Relevés fiscaux" line (ge-2025-guide-declaration-pp p. 43: `statement.value_chf`, `statement.income_a_chf`, `statement.income_b_chf`, `statement.withholding_swiss_chf`); each bank account (instance: IBAN, else account number; `accounts.*`, the form's number being the IBAN's last 8 positions, p. 40); each liability (`liabilities.*`, p. 37); each security (instance: ISIN; `securities.*`, with `securities.value_kursliste` when the bank's tax value comes from the ESTV price list). Client names, client numbers and the statement id are never returned.
- A statement whose segments are incomplete still becomes "Bank e-tax statement" from its eCH-0270 page barcode (Code 128, first three digits 196), for Claude to read.

## Finding the barcodes in a PDF, without native code

1. Images: PDF.js (unpdf) decodes every image of a page (JPEG in JavaScript, Flate, 1-bit masks) to gray. A small image (under 800 pixels wide, such as a 290 x 35 segment with one pixel per module and row) is enlarged with a quiet zone; a page-size image is scanned as is, then once more enlarged 2 times (1.5 for big ones) if no PDF417 was found.
2. Vector barcodes: the page's operator list is walked with its transformation matrix; every filled axis-aligned rectangle is collected with its fill color, dark bar-sized ones are grouped by proximity (a grid, so the cost is near linear), and each group is rasterized in painting order into a bitmap where the narrowest bar is at least 3 pixels, y axis flipped (a mirrored PDF417 can't be read).
3. Pages are visited from the last to the first and the walk stops once a complete set of symbols is found (20 pages at most).

The reader: `zxing-wasm` 3.1.4 (MIT; ZXing-C++, Apache-2.0; stb_image, MIT), reader build only. Measured on this Mac: about 0.1 to 0.7 s per document; the whole offline test of the packaged extension, both barcode documents included, runs in under a second.

## How the WebAssembly loads offline

zxing-wasm's default is to download its `.wasm` from the jsDelivr CDN. Taxpresso never lets it:

- the build copies `zxing_reader.wasm` next to the bundle (`server/zxing_reader.wasm`); `extension/src/main.ts` gives its path at start;
- the file is read from disk, its SHA-256 checked against the one zxing-wasm was built with (`ZXING_WASM_SHA256`), and Taxpresso instantiates it itself (`instantiateWasm`, `wasmBinary`, a `locateFile` that returns the name unchanged): zxing-wasm never builds a URL;
- the bundle's `fetch` and `XMLHttpRequest` are refusing stubs (as for PDF.js);
- the offline test reads both barcode documents in the packaged extension with the network guard in the server process, and in the macOS sandbox with no network: pass, no outbound attempt.

Size: the `.mcpb` grows from 1,186,604 to 1,649,807 bytes (+463 KB, +39 %); unpacked, `zxing_reader.wasm` is 953,527 bytes and the server bundle grows by about 143 KB (3,482,323 to 3,625,859 bytes).

## What was tried and what worked

| Check | Result |
|---|---|
| zxing-wasm writes PDF417 (plain) | Yes, used for test fixtures. It can't write Macro PDF417 (no Structured Append option), so test segments are made from raw codewords with bwip-js (MIT, test dependency only, never shipped). |
| ZXing reads Macro PDF417 index, count and file id; several segments in one image, any order | Yes (the macro block must follow the padding, per ISO/IEC 15438 annex H, or ZXing refuses the symbol) |
| Salary certificate as one JPEG page, PDF417 vertical, modules 2 pixels; 1.75, 1.5 and 1.25 pixels at JPEG quality 70 | Read (the fractional ones only after the enlarged rescan) |
| Salary certificate split over two symbols | Read |
| Barcode drawn as vector rectangles | Read |
| JPEG photo of a barcode | Read |
| e-tax statement: 4 segments of 290 x 35 pixel images, shuffled; one missing; ZIP instead of ZLIB; one plain symbol | Read; "3 of 4 segments" and the kind from the page barcode; read; read |
| Schema failures (two-decimal amounts, missing or unknown elements, AHV format, dates, ISIN check digit, currency codes...) | Not verified, with the reason |
| Text in a document trying to give instructions (box 15) | Stored as the box 15 text; changes nothing |

## What could not be verified

- A real bank e-tax statement: compression, the macro fields banks write, and the 290 x 35 image layout are taken from the standards only.
- A real certificate split over several symbols, a real ELM 6.0 certificate, and a real pension certificate.
- Barcodes drawn with a barcode font (glyphs, not rectangles), as shading or patterns, or rotated by other than multiples of 90 degrees: not read; such documents go to Claude. A full page renderer (as the eCH API's "render" switch does) would need a canvas, which Taxpresso doesn't ship.
- Phone photos of paper certificates: one synthetic photo is read; real photos (blur, perspective) were not tried.

## Decisions for the lead

1. A certificate without `Company` is accepted (the schema requires it). Keep, or refuse as not schema-valid?
2. Whose a certificate is: no names are asked in the questionnaire, so the employee's name can't suggest p1 or p2. Taxpresso assigns p1 in a single household and, in a couple (or before the civil status is answered), waits for the user to choose in the dashboard; the values then fill in. Asking for first names (kept locally) would allow a suggestion.
3. e-tax statements give both the statement totals and every account and security: the engine must use one or the other, never both (the guide p. 43 allows the grouped line).
4. Securities: income is stored as A + B in `securities.income_gross_chf` (as for broker exports); foreign tax as the lump-sum tax credit (`lumpSumTaxCreditAmount`); the additional US withholding and the non-recoverable part are not stored; the federal gross income is used, not the cantonal variant (`grossRevenueACanton`). A security held both at a Swiss bank and at a broker shares one instance (its ISIN): the last reading wins. These need the securities and wealth owners' review.
5. F and G are stored as false when the barcode doesn't tick them; other absent boxes are not stored.

## Go / no-go

Go. Salary certificates with a barcode are read to verified values with their boxes, on the user's computer, without Claude reading them. E-tax statements are ready on synthetic data; the first real one should be checked for its compression and macro fields (`TAXPRESSO_BARCODE_DEBUG=1` prints the diagnostics, no values, to the log).
